# Wizardry 8 Widescreen 1.0.3 (2026-11-14)

The patch now draws the game through its own Direct3D 11 render driver, `Dll\srDD_D3D11.dll`, on
Windows and under Wine alike: dgVoodoo is gone from the package and no wrapper is needed. Under
Wine and Proton (Linux) the patch now starts: run `Wiz8WideSetup.exe` with Wine or Proton, in
any Wine prefix, and press Install; no launch option is needed. The installer has a "Report a
problem..." button, which packs what a bug report needs into one zip. What the release was
tested on, and what it was not, is under "Tested".

## Changes

- The render driver. Up to 1.0.2 the game drew through its own DirectX 7 driver
  (`Dll\srDD_DirectX7.dll`), which on modern Windows needs a Direct3D 7 wrapper: the package
  carried dgVoodoo 2 for that. Since 1.0.3 the package carries `Dll\srDD_D3D11.dll` instead:
  srDD_D3D11 1.0.0, a render driver for the game's SurRender engine that draws the picture the
  DirectX 7 driver drew, on Direct3D 11. The driver is a project of its own, with its own
  version and releases (repository [abr17/wiz8-d3d11](https://github.com/abr17/wiz8-d3d11); in
  this repository the git submodule `drivers\srdd_d3d11`,
  [its README](../../drivers/srdd_d3d11/README.md)), and also works with
  the game without the patch. The patched game always uses it: at every start `wiz8hy.dll`
  writes `3DVideo.CFG` with `D3D11` in line 1 and the chosen resolution (`Canvas.cpp`,
  `DisplayPrepareVideoConfig`; before, `DirectX7`). There is no setting to choose another driver
  and no fallback: the game's own drivers (DirectX7, OpenGL, Glide, Software) stay in the `Dll`
  folder untouched, but the patch does not use them and is not supported with them. It needs a
  graphics card with Direct3D feature level 10_0 (a Direct3D 10 card or newer); "Tested" says
  what it has run on. The package carries the driver's release build, which draws with the fast
  path only (the card's standard Direct3D 11 pipeline): it has no `L2Tier` setting and none of
  the settings of the driver's exact paths, which are in its reference build only, the build its
  tests compare with. A start that cannot make the fast path ends with an error line in
  `Dll\srDD_D3D11.log`; nothing stands in for it. The driver's own zip (`srDD_D3D11-1.0.0.zip`:
  the DLL, its README, `LICENSE`, and the header and helper library for add-on authors) has no
  settings file either: a player who wants settings writes `Dll\srDD_D3D11.ini` by hand (the
  keys are in the driver's README).
  - How the driver draws is in its own documents
    ([fast-path.md](../../drivers/srdd_d3d11/docs/fast-path.md)). Without a card of feature
    level 10_0 it draws with WARP, the software renderer of Windows (slow); `Dll\srDD_D3D11.log`
    names the device it drew with.
  - When the render driver does not start, the game's message says where to look. The original's
    "Video device cannot be started. Please re-run 3DSetup." is now "Video device cannot be
    started: the render driver Dll\<name>.dll is missing, could not be loaded or found no
    graphics device it can use.", followed by what the patch needs (its own driver,
    `Dll\srDD_D3D11.dll`: reinstall the patch if the file is missing; a graphics card of the
    Direct3D 10 class or newer with current graphics drivers) and by the name of the driver's
    log, `Dll\srDD_D3D11.log`, which says what it found. "Could not open video output device."
    now adds "See the log of the widescreen patch's render driver, Dll\srDD_D3D11.log." For the
    first message `InitializeVideoDevice` (`0x00422240`) joins the replaced functions of
    `wiz8hy.dll`: 290 instead of 289.
  - A read-only `3DVideo.CFG` is made writable and rewritten. Before, the write failed without a
    word, `wiz8wide.log` said `rewritten` all the same and the game started with whatever driver
    the file named. When the file cannot be written for another reason, the game starts with
    what the file names and the log says
    `[Display] 3DVideo.CFG could not be written: it had ..., the patch needs ...`.
  - The installer puts the driver next to the game's drivers as one more file of the package. An
    `srDD_D3D11.dll` that was already in `Dll\` (the driver is also published on its own) is
    saved and comes back on uninstall; while the patch is installed, the game runs with the
    package's copy. A `Dll\srDD_D3D11.ini` is not part of the package: one the player made stays
    where it is, and its settings apply to the package's copy too. The driver's logs
    (`Dll\srDD_D3D11.log`, `.log.old`) and `3DVideo.CFG` are in the list of installed files
    (`Wiz8Wide.installed.txt`): uninstall removes the logs and a `3DVideo.CFG` that the patched
    game wrote in a folder that had none (one that was there before the install comes back, as
    before), and so do the installers of 1.0.0 - 1.0.2 when they remove 1.0.3. An update or
    reinstall with the diagnostics mode on (a `Wiz8Logs\` folder) keeps the driver's logs there,
    with the patch's three. The installer no longer installs dgVoodoo (`DDraw.dll`,
    `D3DImm.dll`, `dgVoodoo.conf`), not even from a `files\` folder that still has them from an
    older package. An update from 1.0.0 - 1.0.2 removes the dgVoodoo files that version
    installed and puts back what they had replaced. A copy of `files\` made by hand over such a
    version leaves them: the READMEs say to delete them.
  - Full screen is the driver's: it opens the chosen resolution without changing the monitor's
    mode, covers the monitor and enlarges the picture to fit, with black bars when the
    proportions differ (as dgVoodoo did before, now with the driver's own bicubic filter). A
    resolution the driver does not list starts borderless instead. `wiz8hy.dll` reads the same
    rectangle for the mouse.
  - The package script (`make-hybrid-package.ps1`) takes the driver with `-Driver` (default:
    `drivers\srdd_d3d11\out\srDD_D3D11.dll`) and asks the driver's own checker,
    `drivers\srdd_d3d11\tools\check_dll.py --package` (Python 3), which refuses a DLL that is
    not the release build, does not embed exactly the release build's shaders, has no build
    record of its own beside it, comes from a build that did not check the driver's ABI, or was
    built from another commit of the driver than the present one or from uncommitted changes
    (`-AllowModifiedDriver` makes a trial package of a build from uncommitted changes). The DLL
    that ships is built with MSVC by `drivers\srdd_d3d11\build.ps1` without `-Reference`, which
    compiles the shaders into it: the driver then needs no `d3dcompiler_47.dll` on Windows
    ([building.md](../building.md), section 7).
  - The package has two new files beside the READMEs: `LICENSE`, the patch's licence, and
    `THIRD-PARTY-NOTICES.txt`, the licence of MinHook, which `version.dll` contains.
  - The driver's add-on interface is on (`[D3D11] Extensions=1` in `wiz8ws.ini`): the loader
    passes the camera and the game's water to the driver for add-ons. The package has no add-on,
    and without one nothing changes.
- Under Wine and Proton the patch never started in 1.0.2: Wine maps its own `version.dll` and
  `ddraw.dll` instead of the files of the same name in the game folder, so the main menu showed
  only `v1.2.4` (a player's report). Now it starts in three ways, all of them only under Wine
  (Windows sees none of it; details: [loader.md](../loader.md), "Wine and Proton"):
  - The installer, run under Wine, puts a copy of the patch's `version.dll` in place of the
    game's `binkw32.dll` (the video library, which Wine has no copy of its own of, so it always
    loads the game folder's file) and keeps the original as `binkw32_wiz8wide.dll` and in
    `Wiz8Wide.backup\`. The copy forwards all 83 Bink functions to the original and starts the
    patch: no setting is needed in any prefix. Uninstall puts the original back. If a store's
    file check (Steam's "Verify integrity of game files", a GOG Galaxy or Heroic repair) brings
    the original `binkw32.dll` back, the installer shows it and offers "Reinstall".
  - The installer writes the per-program Wine setting for `Wiz8.exe` into the prefix it runs in
    when the game runs there (`HKCU\Software\Wine\AppDefaults\Wiz8.exe\DllOverrides`:
    `*version` = `native,builtin`, `*ddraw` = `builtin`; in a 32-bit prefix also a plain
    `ddraw` = `builtin`, since such a prefix looks Wine's own `ddraw.dll` up by that name first
    and a global `ddraw=native` would win otherwise), only where the player has set neither
    name, and notes in the prefix what it wrote, so that uninstall removes only that.
  - The patch itself, once started under Wine, writes the same setting into the game's prefix
    by the same rules, so the game keeps starting with the patch even after a file check has
    restored `binkw32.dll`.
  - For a copy of `files\` made by hand, the first start needs the launch option
    `WINEDLLOVERRIDES="version=n,b;ddraw=b" %command%`; the patch then keeps the setting itself.
- The installer finds the game under Wine: the GOG version added to Steam as a non-Steam game,
  Heroic, Lutris, the GOG key (a plain GOG install in the same prefix) and Steam. The window
  says where it found the game ("Found by ...") and whether the game runs in this prefix. The
  folder box also takes a pasted Linux path (`/home/deck/Games/Wizardry 8`), and Browse opens at
  the home folder. Its last message says whether the patch will start by itself; only when it
  cannot set up the `binkw32.dll` start (another mod's `binkw32.dll`) and the game runs in
  another prefix does it ask for the launch option, which it then puts on the clipboard.
- Under Wine the game's 3D goes through the same Direct3D 11 driver (Proton: DXVK; plain Wine:
  its own Direct3D 11), and its 2D DirectDraw through Wine's own `ddraw.dll`. The `*ddraw` =
  `builtin` setting above keeps it that way when a `DDraw.dll` is left in the game folder:
  dgVoodoo 2.8.7.5 (the one 1.0.2 installed) crashes under every Wine at its first surface (Wine
  bug 58731), and Wine 11.6 and later would load it by default. A game folder installed under
  Linux also works from Windows as it is (dual boot): nothing more has to be installed there.
- Plain Wine 9.0 (the Wine of Ubuntu 24.04): in the world the 3D view was black behind the
  interface. The game keeps the transparency of its 2D layer in bit 15 of a 5:5:5 DirectDraw
  surface that has no alpha mask. Windows' DirectDraw and Wine 10 write a colour fill's value
  as it is; Wine 9.0's `IDirectDrawSurface::Blt(DDBLT_COLORFILL)` sets bit 15 in every pixel of
  such a surface, so the first fill (the hit point numbers on the portraits) made the whole
  layer opaque. `wiz8hy.dll` now fills 16-bit surfaces itself through `Lock`
  (`FillSurfaceRectDirect` in `decomp\src\sgp\vsurface.cpp`, behind `FillSurface` and
  `FillSurfaceRect`, which every fill of the game goes through), with the same result on
  Windows.
- Full screen under Wine is the driver's as on Windows: a borderless window at the monitor's
  size, the picture drawn at the chosen resolution and enlarged into it with black bars; the
  monitor keeps its own mode, and the mouse lands where it points. (Wine itself would switch the
  monitor's mode under X11 and leave it switched after a crash, and stretch the picture under
  Wayland.)
- `version.dll`: when the system `version.dll` cannot be loaded (under Wine with the wrong
  launch option `version=n` instead of `version=n,b`), its functions now report failure
  instead of crashing, and `wiz8ws.log` says why. Under Wine the log names the `ddraw.dll` that
  was loaded, the way the patch started (`started from binkw32.dll (no launch option needed)`)
  and the Wine setting it wrote.
- Defaults and logs. Without a `wiz8ws.ini`, or with one that lacks the `[Hybrid] Enabled` or
  the `LogWindowCalls` line, the patch now behaves as with the shipped file: the widescreen
  engine (`wiz8hy.dll`) is loaded, and `wiz8ws.log` does not get a line for every window the
  game creates (before, the loader's older hooks ran instead of the engine, and the log got
  those lines). `[Hybrid] Enabled=0` is not supported; `[General] Enabled=0` switches the patch
  off. In `wiz8ws.log` the two lines that began with `phase4:` begin with `hud layout:`, and the
  `hybrid:` line counts 290 replaced functions. `wiz8wide.log` says at every start how the
  picture reaches the screen: `[Display] output: borderless, no scaling`,
  `[Display] output: window, no scaling` or
  `[Display] fullscreen WxH: scaled into WxH at (X,Y) of the WxH window`.
- Character creation, the page with the name, portrait, personality and voice: while a voice
  sample plays, the stone beside the window darkens with the window. The game darkens its
  640x480 window for as long as the sample's box is up; since 1.0.0 the stone at the sides of a
  wide screen stayed bright. Now it is darkened through the game's own shade table, by the same
  amount, and painted afresh in the frame in which the window becomes bright again
  (`UpdateWideSideWingsShade` in `decomp\src\wiz8\engine_code\WideArt.cpp`, called from the
  replaced `RenderFrame`; no function joins the replaced ones for it).
- The video of the Dark Savant ending is shown. It is the one video that the game starts
  straight from the main game screen, where the 2D layer is in the mode in which a pixel with
  its top bit clear is a hole (the HUD lies over the 3D view that way), and the video player
  writes exactly such pixels. Since the videos go through the 2D canvas, the picture of this
  video therefore never reached the screen: in the test the screen kept the last picture of the
  game for the minute and a half of the video; in play the game's own fade to black comes
  first, so the screen would stay black (this follows from the code; it was not run). The
  video screen now turns that mode off when it opens and marks the whole canvas for upload
  (`IntroScreenEnter` in `decomp\src\wiz8\local_screens\IntroScreen.cpp`, one of the replaced
  functions already); the main game screen turns the mode on again when the game comes back.
  The frame after a video now starts on a black back buffer (a whole clear, once, asked for by
  `FinishVideoPresentation` and done in `RenderFrame`): the videos share the back buffer with
  the game, and on a canvas 640 wide the last picture of this video would otherwise show around
  the 3D view for one frame. The fault was found in the checks of this release; the released
  1.0.2 has it.
- After the video of the Dark Savant ending the black fade covers the whole wide screen. Its
  quad was made on the video screen, 640 wide, and for two frames the widened view showed left
  and right of it. The quad now takes its width from the canvas, not from the layout of the
  moment it is made (`FullscreenQuadWidth` in
  `decomp\include\wiz8\local_screens\MainGameLayout.h`, used by the replaced
  `BeginScreenFade`). Every other fade is made on the main screen and is unchanged.
- Options with `WideWindows=0` on a canvas 856 wide: the inner 4 pixels of the stone at both
  sides were black for one frame when the screen opened and after each of its dialogs. The
  screen now paints the stone again in the frame in which it clears the surface.
- Known and left as it is: spell flashes that the game ties to the camera are animations made
  for the 4:3 view; on a wide screen they fill the middle of the view. The patch stretches
  nothing, so they stay as the game draws them.
- Installer, also on Windows: an empty or relative game folder is refused with the "does not
  contain Wizardry 8" message. Run from inside the game folder without a GOG key, the 1.0.2
  installer showed an empty folder box, and Install left a folder named `D3DImm.dll` there. A
  relative `--install` or `--uninstall` folder on the command line (`--install .`) is read
  against the current folder, and a game at a drive root (`G:\` in the GOG key) is found and
  installed as in 1.0.2. A package whose `files\` folder lacks `version.dll`, `wiz8hy.dll`,
  `wiz8hy_hooks.txt`, `wiz8ws.ini` or `Dll\srDD_D3D11.dll` (an archive unpacked in part, a file
  taken by an antivirus program) is refused: the message names the missing file and nothing is
  changed; before, such an install reported success. An original `3DVideo.CFG` that cannot be
  saved fails the install with the "Could not copy a file" message.
- Bug reports made easy. The installer has a "Report a problem..." button: it saves one zip to
  the Desktop (under Linux: the Desktop or home folder) with the settings, the list of installed
  files, the patch's and the render driver's logs, what the diagnostics mode kept in `Wiz8Logs\`
  (logs of earlier sessions, crash dumps) and a `report.txt` with the patch version, the game
  version, Windows or Wine, processor, memory, graphics cards with driver versions and the
  screen. `report.txt` also says which program files are in the game folder, without packing
  them: the render driver, `version.dll` and `wiz8hy.dll` with size, time and SHA-256;
  `binkw32.dll`, `DDraw.dll`, `D3DImm.dll` and `dgVoodoo.conf` with size and time, or as absent.
  When the Desktop cannot be written, the zip goes to the temporary folder, never to the game
  folder. The installer puts the zip's path on the clipboard and offers to open the bug report
  form on GitHub with the patch version, the system and the graphics card filled in; the player
  describes the problem and adds the file. The installer sends nothing itself and only reads the
  game folder. The archive stays under GitHub's 25 MB: the settings go in first, then the last
  session's logs, then `Wiz8Logs\` newest first, and a file that would take it over 24 MB is
  left out. A log over 8 MB goes in as its first 1 MB and its last 7 MB, with a line between
  them that says how much is left out. `report.txt` names every file left out, with the reason,
  and marks a cut log; the installer's last message says when not everything fit. Without the
  window: `--report "<folder>" ["<file.zip>"]`. The repository has a bug report form
  (`.github\ISSUE_TEMPLATE\bug_report.yml`), and the READMEs say where reports go; before, they
  said "send the logs" without saying where ([loader.md](../loader.md), "The report file").
- READMEs (English, Russian, German, French): the requirements as what the render driver needs
  (a graphics card of the Direct3D 10 class, feature level 10_0) and what the patch was tested
  on; where to look when the picture is missing or very slow (`Dll\srDD_D3D11.log`); the render
  driver, the patch's own copy of it and what to do with dgVoodoo files left by a hand-made copy
  of an older version; that `[General] Enabled=0` leaves the game on the render driver named in
  `3DVideo.CFG`; and a Linux / Steam Deck section: running the installer with Wine or Proton
  from Steam, Heroic, Lutris, Bottles or plain Wine, what to do after a store's file check, the
  launch option for a hand-made copy, the letter case of the game's folders for such a copy, and
  dual boot. The comments of `wiz8ws.ini` say the same about `[General] Enabled=0`, and that
  `[Hybrid] Enabled=0` is not supported.
- For developers: `version.dll`'s build checks its 83 Bink forwarders with `llvm-readobj` (an
  older lld writes wrong forwarder names, so build it with llvm-mingw only), and the package
  script repeats the check; `scripts\linux\` is an isolated Linux test bench (Docker Desktop,
  Ubuntu's Wine 9.0 and GE-Proton, a fresh prefix and game copy for every run, no network;
  [testing.md](../testing.md), "Linux / Proton bench"); the `wiz8hy.dll` build stops when a
  function of the game source carries a change marked "Mod" and is not among the replaced
  functions, so that an edit cannot stay out of the DLL unnoticed ([hybrid.md](../hybrid.md),
  "How to change a game function"); the installer's tests have four new scenarios, S9 - S12
  (started in the game folder, the report file, a game folder without `3DVideo.CFG`, a package
  without the render driver), and the report's archive writer has a test of its own that needs
  no Windows ([testing.md](../testing.md), "The installer's tests").

## Tested

What the patch and its render driver have run on:

- a laptop with an NVIDIA RTX 4080, Windows 11: the game played, on the builds up to the morning
  of 14 November, before the two changes for the ending video (the last row of the table);
- Windows Sandbox: the automated checks;
- Wine and Proton: only the Linux test bench, a Docker container with software rendering
  (GE-Proton10-25 and Ubuntu's Wine 9.0; [testing.md](../testing.md), "Linux / Proton bench").

How the render driver is checked on its own:
[verification.md](../../drivers/srdd_d3d11/docs/verification.md).
